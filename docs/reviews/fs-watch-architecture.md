# Вердикт

**Есть блокеры для установки экспериментального демона и для upstream PR.** Ветка пригодна для обсуждения как opt-in прототип, но обещание «страховочная проверка каждые десять минут» сейчас сильнее реализации. Главные проблемы — планирование восстановления, отсутствие отдельного цикла достижения стабильности и непрозрачное состояние watcher после ошибок.

Проверен только приложенный snapshot. Исходников notify/backends, `Cargo.lock`, background-бинарника и упаковочных сценариев нет; их поведение не предполагается доказанным. Результаты ранее пройденных тестов не подтверждают отсутствующие сценарии.

Все пути ниже относительны корню репозитория.

## Ранжированные находки

### 1. Десятиминутный таймер не ограничивает время восстановления watcher

**Подтверждено по исходнику; высокий приоритет.**

**Место:** `iroh-share-watch/src/lib.rs:129–155`; вызывается из `iroh-share/src/transfer.rs:105–128`.

Каждый вызов `wait()` создаёт новый `sleep(delay)`. Любое событие или manual refresh завершает ожидание и уничтожает таймер. При следующем входе отсчёт начинается заново. Дополнительно `biased` ставит manual и события перед таймером.

**Сценарий:** watcher потерял часть рекурсивных регистраций, но продолжает выдавать события по доступным каталогам. Проверки fingerprint идут, однако принудительный rearm на страховочном таймере может никогда не выполниться.

Важно различать:

- события действительно запускают полные проверки, поэтому **сами проверки не обязательно голодают**;
- отдельная периодическая операция восстановления регистрации **может голодать неограниченно**;
- десять минут также не ограничивают завершение проверки/публикации: импорт, backpressure и нестабильное дерево могут занимать неопределённое время;
- таймер Tokio не является гарантией пробуждения Android из сна.

**Минимальное исправление:** хранить абсолютный deadline страховочной операции между вызовами; обслуживать просроченный deadline независимо от потока событий. Разделить сроки проверки, восстановления watcher и повторения failed import. Исправить формулировку `README.md:55`.

### 2. После несовпавших fingerprint нет гарантированной скорой повторной проверки

**Подтверждённый дефект планирования; проявление зависит от доставки событий.**

**Место:** `iroh-share/src/transfer.rs:122–128`.

Если первая и вторая проверки различаются, выполнение возвращается к `changes.wait()`. Нет самостоятельного короткого таймера продолжения stability check.

**Сценарий:** событие запускает первую проверку, файл меняется до второй; последнее изменение не получает собственного события — такой класс пропусков уже отмечен в контексте. Следующее событие отсутствует. Вместо скорого подтверждения стабильности задача ждёт до 600 секунд.

При надёжной доставке очередного события это часто маскируется pending generation, но recovery не должен зависеть от этого.

**Последствие:** debounce превращается из самостоятельного механизма сходимости в механизм, требующий дополнительных уведомлений.

**Минимальное исправление:** после обнаружения отличия входить в состояние `dirty/stabilizing` и повторять проверки по короткому таймеру независимо от новых событий. Добавить ограничение частоты и backoff; не обещать публикацию постоянно изменяющегося дерева.

### 3. Ошибка callback не переводит монитор в деградированный режим

**Подтверждено; высокий приоритет.**

**Место:** `iroh-share-watch/src/lib.rs:79–97,116–126`; fallback создаётся только в `iroh-share/src/transfer.rs:62–66`.

Ошибка callback означает только увеличение generation и установку `rearm`. После неё:

- интервал остаётся 600 секунд;
- предпринимается только повторный `watch(root)`;
- watcher не пересоздаётся;
- parent не регистрируется заново;
- причины и результаты восстановления не логируются.

**Сценарий:** первоначальная регистрация успешна, затем backend сообщает ошибку, после которой перестаёт доставлять события. Полная проверка может пройти успешно, поэтому `job.state` не станет `Failed` и 30-секундный retry не включится.

**Последствие:** деградированный watcher выглядит здоровым, хотя обещанный минутный polling относится лишь к ошибке первоначальной установки.

**Минимальное исправление:** явные состояния `Watching / Degraded / Polling`, структурированная диагностика, минутная проверка в degraded-состоянии и ограниченные попытки пересоздания watcher с регистрацией parent и root.

Overflow/rescan разумно трактовать как необходимость полной проверки. Но **успешная проверка содержимого не доказывает восстановления доставки событий**.

### 4. Root replacement поддержан лишь частично; lifecycle регистрации не определён

**Подтверждённые пробелы плюс backend-зависимые гипотезы.**

**Место:** `iroh-share-watch/src/lib.rs:84,92,101–104,116–125`.

Подтверждено:

- при rearm регистрируется только root;
- после первоначального setup failure `polling_only()` больше не пробует включить watcher;
- в `rearm_if_needed(true)` short-circuit на строке 117 не выполняет `swap(false)`: уже установленный флаг остаётся и вызывает дополнительную попытку регистрации;
- фильтр допускает пустые paths, ошибки и rescan независимо от sibling filtering. Поэтому комментарий «siblings never trigger scans» слишком категоричен.

**Гипотезы, требующие проверки конкретного backend:**

- повторный `watch(root)` может не заменить stale-регистрацию после rename;
- старое перемещённое дерево может остаться зарегистрированным;
- повторные регистрации могут быть дорогими или неидемпотентными;
- удаление/replacement parent может разрушить механизм обнаружения восстановления root;
- событие только с путём parent будет отфильтровано, даже если обозначает изменение root;
- пути через заменивший root symlink могут не соответствовать lexical prefix фильтру.

Нельзя назвать это доказанной утечкой notify без его исходников.

**Минимальное исправление:** определить поддерживаемые переходы root/parent и стратегию reconciliation регистраций. Запрос rearm снимать **перед** попыткой, включая forced-путь; при неудаче возвращать его. Для сложных переходов рассмотреть пересоздание watcher вместо слепого повторного `watch()`.

Отдельно: `iroh-share/src/main.rs:583–588` canonicalize исходный share path. Поэтому retarget исходного пользовательского symlink уже не меняет сохранённый target. Это свойство существующей модели путей, а не автоматически ошибка нового watcher.

### 5. Coalescing ограничивает очередь, но не стоимость обработки

**Подтверждённая архитектурная проблема; тяжесть зависит от нагрузки.**

**Место:** `iroh-share-watch/src/lib.rs:97`; `iroh-share/src/transfer.rs:122,136–161`; синхронная регистрация — `iroh-share-watch/src/lib.rs:101–104,123`.

Каждое полученное поколение запускает полный обход дерева. Если fingerprint равен `last`, нет даже секундной паузы. Поток metadata-событий способен поддерживать почти непрерывные scans без изменения публикуемого содержимого.

Coalescing — **не rate limiting**. Callback всё равно обрабатывает каждое событие. Fingerprint хранит строки всех файлов и дополнительно создаёт объединённую строку; стоимость зависит от суммарной длины путей. Каждый share получает отдельный watcher, включая overlapping shares.

Регистрация/rearm вызываются синхронно внутри async worker. Их длительность на больших деревьях неизвестна и потенциально блокирует executor thread.

**Минимальное исправление:** минимальный интервал между scans, ограничение параллельных обходов/imports между shares, измеримые счётчики событий/scans/rearms. Дорогие операции регистрации вынести из executor hot path.

Read-access фильтр полезен, но отсутствие feedback от reads на всех backends не доказано: иные backend-события проходят через `_ => true`.

### 6. Отдельный crate усложняет packaging без показанного второго потребителя

**Подтверждено по manifest; средний приоритет.**

**Место:** `iroh-share/Cargo.toml:13–15,37`; `iroh-share-watch/Cargo.toml:1–12`; корневой `Cargo.toml:2–4,29`.

Optional feature описан правильно: в показанном manifest daemon по умолчанию не включает helper. Добавление workspace member само по себе не включает notify в daemon graph. Однако workspace-wide сборка helper — другой случай, и её нельзя смешивать с feature-off daemon.

Проблемы:

- helper указан только через `path`, без `version`: это препятствие для crates.io-публикации пакета daemon;
- порядок публикации и владение отдельным пакетом не определены;
- workspace Tokio уже имеет `full`; helper не становится узкой зависимостью благодаря добавлению `sync,time`;
- manifest допускает notify `8`, а не доказывает использование именно 8.2; lock отсутствует;
- feature propagation в background-бинарник и release packaging проверить невозможно.

**Минимальное исправление:** для одного потребителя — приватный feature-gated модуль и optional notify непосредственно в daemon. Если crate сохраняется, нужны version+path, публикационная стратегия и проверка всех бинарников.

Название `fs-watch` приемлемо. Но compile-time opt-in включает новую политику **для всех shares**; runtime выбор режима на share отсутствует.

### 7. Manual refresh — не универсальный recovery-механизм

**Подтверждено; ограничение существующей политики, не доказанная новая регрессия.**

**Место:** `iroh-share/src/main.rs:546–575`; `iroh-share/src/transfer.rs:113–115`.

Refresh запрещён для:

- file roots;
- отсутствующего root;
- share без managed name;
- текущего импорта.

При принятии запроса он обходит двухскановую проверку и запускает импорт, а не только fingerprint.

**Последствие:** «manual refresh available» не означает доступного обходного пути для всех проблем watcher. Существующая политика ограничивает и альтернативу manual-only.

**Минимальное исправление:** документировать ограничения. Если manual предлагается как recovery, разрешить его для всех shares и определить отдельно «проверить» и «принудительно импортировать».

### 8. Тесты не доказывают заявленные recovery-свойства

**Подтверждено; существенный пробел перед установкой.**

- `iroh-share-watch/src/tests.rs:120–134`: тест с названием full-tree refresh проверяет `Wake::Changed` и существование файла. Fingerprint/import вообще не вызываются.
- `.../tests.rs:153–182`: `after.txt` — непосредственный ребёнок root, его событие может прийти от parent watch. Тест может пройти **без восстановления recursive watch**.
- `.../tests.rs:168–175`: десять попыток drain не гарантируют опустошение; позднее старое событие способно удовлетворить финальную проверку.
- `.../tests.rs:138–149`: 250 мс без wake не исключают отложенного sibling-события.
- `iroh-share/src/transfer.rs:1174–1223`: debounce-тест принимает любое последующее `Seeding`, не проверяя collection hash и финальные bytes. При задержке исполнения после первого write промежуточная версия может стабилизироваться до второго write, делая тест времязависимым.
- `.../tests.rs:75–89` проверяет заранее накопленные generations, но не реальную гонку импорта, cancellation или события между двумя scans.

Paused-time тесты хорошо подходят для планирования, однако сейчас проверяют преимущественно одиночные waits, а не переходы состояний.

## Ограничения consistency: отделить от нового watcher

По контексту это сохранённые свойства; без baseline diff их происхождение окончательно не доказать.

**Места:** `iroh-share/src/transfer.rs:71–87,122–125,134–161,415–478`.

- Fingerprint хеширует metadata, не содержимое. Равенство двух обходов не доказывает целостный snapshot.
- Две scan-ошибки превращаются через `.ok()` в равные `None`: «стабильная ошибка» может разрешить попытку импорта.
- После импорта нет валидации соответствия результата fingerprint до импорта.
- `TryReference` плюс удержание `TempTag` не гарантируют неизменяемости внешних файлов. Точное поведение blobs отсутствует в snapshot.
- Предыдущая коллекция удерживается до успешной замены, но не вся история. Rooting не равнозначен доступности прежних bytes или непрерывному announcement: `main.rs:469–476` выбирает только `Seeding`.

Новый watcher эти ограничения не создаёт автоматически, но увеличение периода reconciliation до 600 секунд увеличивает продолжительность некоторых несогласованных состояний.

## Альтернативные архитектуры

| Вариант | Преимущества | Цена |
|---|---|---|
| **Настраиваемый polling + manual** | Минимум backend-переходов; предсказуемая стоимость | Задержка обнаружения и периодические обходы |
| **Приватный notify-модуль + независимый scheduler** | Нет лишнего пакета; чёткое разделение hints и consistency | Нужна явная state machine |
| **Текущий helper как транспорт событий** | Изоляция notify, потенциальное переиспользование | Packaging/API; scheduler следует убрать из helper |
| **Общий watcher manager для всех shares** | Общие регистрации, дедупликация overlap, бюджеты | Более сложные routing и lifecycle; пока преждевременно |

**Рекомендация:** для телефона ближайший консервативный вариант — настраиваемый polling. Для notify PR — приватный модуль, выдающий dirty/health signals, и отдельный scheduler с абсолютным safety deadline, rate limiting и stability retry. Отдельный crate оправдан при реальном втором потребителе или самостоятельной проверяемой границе API, не просто ради короткой обёртки.

## Фокусированный план регрессионных тестов

Без выполнения; только synthetic temp data и loopback endpoints.

1. **Планирование:** paused time, события каждые несколько секунд дольше двух safety periods; проверить принудительный rearm по deadline, ограничение числа scans и отсутствие starvation от manual.
2. **Сходимость:** второй fingerprint отличается, затем никаких событий. Проверить скорую повторную проверку и публикацию последней версии.
3. **Generation/cancellation:** отменить незавершённый wait, затем проверить pending wake; barriers вокруг scan/import, событие после snapshot — повторная reconciliation.
4. **Recovery:** injectable watcher adapter; setup failure → доступный root, callback error, rescan, ошибка rearm → успех. Проверять режим, интервалы и регистрацию обоих путей.
5. **Native lifecycle:** после replacement root менять **глубоко вложенный** файл, невидимый nonrecursive parent watch. Отдельно file replacement, длительное отсутствие root, parent replacement, symlink policy.
6. **Результат публикации:** проверять ожидаемые collection hash, paths и bytes; считать imports и исключать промежуточную публикацию. Сохранять прошлый tag при injected import failure.
7. **Ресурсы:** синтетические большие/overlapping trees, metadata storms, длительное чтение опубликованных файлов; учитывать scans, CPU, RSS, registrations и время setup.

## Что сохранить и что упростить

**Сохранить:** feature-off двухсекундный polling, регистрацию до импорта, ограниченный generation channel, трактовку событий как hints для полного обхода, удержание прошлой коллекции до успешной замены.

**Упростить:** один пакет при одном потребителе; убрать из транспорта событий решения о debounce и retry. Заменить неявные `failed/rearm/fallback` на небольшую явную state machine. Не расширять публичную конфигурацию всеми таймерами до определения контрактов.

## До установки на телефон и до PR

**До установки:** закрыть находки 1–4, усилить recovery-тесты, дождаться feature-on/off проверок обоих daemon-бинарников. Использовать отдельный staged binary/state и заранее определить rollback. На тестовом дереве Documents проверить обычные записи другого Android-приложения, suspend/resume и длительный idle. Задать бюджеты scans, CPU/RSS и регистраций.

Измеренные 5,5% и 0,6% CPU относятся к polling-вариантам, **не доказывают экономию notify и не являются измерением батареи**.

**До upstream PR:** проверить backend lifecycle по исходникам и поддерживаемым платформам, packaging/installability и dependency graphs; сформулировать границы detection/recovery, убрать необоснованные гарантии из README, представить измерения idle и storms. Непроверенные Android/non-Linux сценарии должны оставаться явно обозначенными ограничениями, а не скрываться за зелёными тестами.
